# Django CMSの公開記事が無権限で書き換えられた――認可を「画面」ではなく「状態遷移」で直す

> この記事は下書きです。公開前に、実際の配備環境で行う最終確認の結果を追記します。

CMSには、記事を書く人、内容を確認する人、公開する人がいます。
画面上では役割がきれいに分かれていても、裏側に一つでも権限確認の弱い更新経路が
残っていれば、承認フロー全体が迂回されます。

今回見つかったのは、まさにその問題でした。

編集権限を剥奪された記事所有者でも、自動保存APIまたはリビジョン復元を使うと、
公開済み記事の本文を書き換えられました。記事の状態は公開中のままです。
つまり、レビュー担当者が一度も見ていない文章が、そのまま公開ページへ現れます。

通常の編集画面を閉じるだけでは直りません。
必要だったのは、CMSに存在するすべての状態遷移を洗い出し、
「誰が、どの記事を、どの状態からどの状態へ変えてよいか」を
一つずつテストで固定することでした。

## 何が起きていたのか

従来の編集判定は、次のいずれかに当てはまれば記事を編集できる設計でした。

- 記事の所有者である
- staffユーザーである
- レビュー権限を持っている

一見すると自然に見えます。しかし、ここでは異なる概念が混ざっています。

「記事を所有している」は、過去にその記事を書いたという関係です。
現在も変更権限を持っていることまでは保証しません。

「staffである」は、Djangoの管理画面へ入れることを示す属性です。
すべての記事を編集・承認・公開してよいという意味ではありません。

さらに、自動保存とリビジョン復元では、通常の編集画面とは別の処理が
Articleを直接更新していました。そこでは change_article や publish_article、
記事の公開状態が十分に確認されていませんでした。

この組み合わせにより、通常画面の権限制御を通らずに公開本文を変更できていました。

## 最初に「拒否後も何も変わらない」テストを書く

セキュリティ修正では、HTTP 403や409が返るだけでは不十分です。
レスポンスが拒否でも、その直前に本文だけ保存されていれば攻撃は成功しています。

そこで最初に、攻撃手順を回帰テストとして再現しました。

- 権限を剥奪した所有者が自動保存しても、本文と公開状態は変わらない
- 権限を剥奪した所有者がリビジョンを復元しても、本文と公開状態は変わらない
- 無関係なstaffは、他人の記事を編集・プレビューできない
- 公開中の記事へ自動保存しても、公開本文は上書きされない
- 正当な執筆者は、自分の下書きを従来どおり編集してレビュー依頼できる

まずテストが失敗することを確認し、それから実装を変えます。
拒否経路だけでなく、正規の執筆経路も同時に残すことが重要です。
守りを強くした結果、誰も記事を書けなくなってはCMSとして成立しません。

## 認可を共通の不変条件にする

修正後、記事を変更するには次の二条件を同時に満たす必要があります。

1. 現在も change_article 権限を持っている
2. 自分の記事である、または review_article 権限により全記事を扱える

考え方を簡略化すると、次のようになります。

```text
変更可能 = change_articleを持つ
         AND（記事所有者である OR review_articleを持つ）
```

この判定を通常フォームだけに置かず、自動保存、プレビュー、リビジョン、
Django Adminを含むすべての変更入口で共有しました。

公開操作はさらに強い状態遷移です。
レビューできるだけでは公開できず、review_article と publish_article の
両方を要求します。staff属性だけでこの判定を迂回することもできません。

ポイントは、URLや画面単位で権限を考えないことです。
「Articleを変更する」「レビュー済みの内容を公開する」という操作単位で
不変条件を決め、それをすべての入口から呼び出します。

## 公開版を直接編集しない

現在のデータモデルには、公開中のスナップショットとは別に編集できる
作業コピーがありません。この状態で公開記事を自動保存すると、
保存先は公開ページが読んでいるArticleそのものになります。

そのため今回は、公開中の記事に対する自動保存をHTTP 409で拒否しました。
リビジョン復元も本文へ触れる前に拒否します。

将来、公開したまま次の版を長期間編集したい場合は、
公開スナップショットと作業コピーを別に持つ設計が必要です。
公開行を一時的な下書きとして使うと、本文だけでなく検索、RSS、キャッシュ、
OGPなど別の経路にも未承認内容が漏れる可能性があります。

今回は「安全に保存できる場所がないなら保存しない」という、
明確で安全側の挙動を選びました。

## レビュー後の差し替えも公開させない

認可を直しても、もう一つ競合があります。

レビュー担当者が内容を確認してから公開ボタンを押すまでの間に、
執筆者が自動保存するとどうなるでしょうか。
公開処理が現在のArticleをそのまま公開すれば、レビュー担当者が見ていない本文を
公開することになります。

この競合を防ぐため、レビュー画面を表示した時点のArticle.versionを
承認フォームへ結び付けました。公開時には記事行をロックし、
現在のversionが確認時と一致する場合だけ公開します。

自動保存とリビジョン復元も、状態とversionの確認から保存までを
同じ記事行のロック内で行います。

これにより、次のどちらかになります。

- 確認した版が変わっていなければ公開できる
- 確認後に本文が変わっていれば公開を中止し、再レビューを求める

「たまたま最後に保存した処理が勝つ」のではなく、
レビューした版だけを公開する仕組みです。

## ログイン周辺のDoSと情報漏えいも閉じる

記事認可のほかに、認証レート制限にも問題がありました。

リバースプロキシ配下では、アプリが本当のクライアントIPを正しく選べないと、
すべての利用者がNginxコンテナの同じIPに見えます。
攻撃者がログインやパスワードリセットのレート枠を使い切れば、
無関係な利用者まで認証できなくなる状態です。

アプリ側とdjango-allauthが同じ信頼プロキシ段数を使うようにし、
値が構成と合わなければ起動時に拒否するようにしました。
回帰試験では、異なるクライアントIPが別々に認識されることと、
利用者が追加した偽のX-Forwarded-Forを信頼しないことを確認します。

ただし、信頼プロキシ段数は配備経路によって変わります。
CDNを追加する場合は段数を再検討し、オリジンへの直接接続も
ファイアウォールで遮断しなければなりません。

ログインだけで閲覧できた管理ダッシュボードも見直しました。
一般ユーザーには予約記事のタイトル、執筆者、公開予定日、内部件数を返しません。
CMS権限を入口で要求し、レビュー担当者以外の一覧と集計は本人の記事へ限定します。
コメント保留件数も、コメントを管理できる利用者にだけ表示します。

MFAの対象もstaff属性だけでは決めません。
公開、承認、削除など高影響の権限を持つ非staffユーザーにもMFAを要求します。

## アプリの外側も本番境界として扱う

認可が正しくても、平文バックアップや認証のないRedis、
毎回中身が変わるコンテナイメージが残っていれば、本番投入の条件は整いません。

今回、アプリの外側も次のように見直しました。

### 通信とコンテナ境界

- NginxでTLS 1.2/1.3を終端する
- HTTPはコンテンツを返さずHTTPSへリダイレクトする
- 公開HTMLへリクエストごとのnonceを持つCSPを付ける
- Redisへパスワード認証を要求する
- Nginxはfrontend、DBとRedisはinternalなbackendへ分離する
- NginxコンテナからRedisを直接名前解決できない構成にする

### 起動とreadiness

- migrationとcollectstaticは一度だけ動くrelease jobへ分離する
- 通常のweb再起動では未適用migrationの有無だけを確認する
- migrationが失敗した場合はwebを起動しない
- readinessでDBとRedisの実接続を確認する
- 依存サービスの障害時は、内部情報を出さずHTTP 503を返す
- Nginx自身のhealthcheckも実際のHTTPS経路を通す

### バックアップとサプライチェーン

- バックアップディレクトリを0700、暗号化ファイルを0600にする
- DBとmediaをAES-256-CBCとPBKDF2で暗号化する
- HMAC-SHA-256を付け、復号前に改ざんを拒否する
- HMAC鍵の値をプロセス引数へ載せず、権限制限した鍵ファイルから直接読む
- 復旧訓練は使い捨てDBと一時mediaディレクトリだけを使う
- Pythonの推移的依存をハッシュ付きlockファイルへ固定する
- Python、PostgreSQL、Redis、Nginxのイメージをdigestで固定する
- 鍵、ローカル証明書、バックアップをDockerビルド対象から除外する

依存関係スキャナーが「既知の脆弱性0件」と報告しても、
今回のようなアプリ固有の認可不備は見つかりません。
依存関係の監査と、状態遷移を対象にしたテストは別の防御です。

## どこまで検証したか

最終的に、Djangoの全363テストが成功しました。
単体テストだけでなく、ローカルの実Compose構成でも次を確認しています。

- migration用jobが正常終了した後にwebとNginxが起動する
- HTTPSでトップページとhealthcheckへアクセスできる
- CSP、HSTS、nosniffなどのセキュリティヘッダーが付く
- HTTPアクセスがHTTPSへリダイレクトされる
- TLS 1.1は拒否され、TLS 1.2と1.3は接続できる
- Redisは未認証のPINGを拒否し、認証時だけ応答する
- Redis停止中はreadinessが503になり、復旧後は200へ戻る
- Nginxはbackendへ参加せず、Redisを名前解決できない
- DBダンプとmediaを使い捨て領域へ復元できる
- 暗号文の改ざんをHMAC検証で拒否できる

独立した再レビューでも、修正対象として残る具体的な指摘がないことを確認しました。

## それでも、実環境での最終確認は残る

ここまでで、リポジトリ内の本番候補構成とローカル再現環境は整いました。
しかし、ローカルでテストが通ることと、本番配備が安全であることは同じではありません。

公開前には、実際の環境で少なくとも次を確認します。

- 実証明書の発行、更新、期限監視
- DNS、ファイアウォール、CDNとオリジンの到達制御
- 実際のプロキシ段数とクライアントIPの取得
- メール送信、パスワードリセット、WebAuthnを含む認証フロー
- バックアップ鍵の保管、オフホスト転送、定期的な復元訓練
- コンテナOSパッケージと実行中イメージの監査
- デプロイ後の公開記事、管理画面、readiness、ログの確認

セキュリティ修正の完了条件は、パッチを書いたことでも、
テストが緑になったことだけでもありません。

元の攻撃手順が失敗し、拒否された後のデータが変わらず、
正規の執筆・レビュー・公開フローが維持され、
実際の配備経路でも同じ境界が守られていること。

今回の修正で最も大きかった学びは、認可を「この画面を開けるか」ではなく、
「この状態遷移を実行してよいか」として設計することでした。
